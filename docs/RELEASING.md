# Как выпускать версии

Сборкой занимается GitHub Actions (`.github/workflows/release.yml`), раздачей —
релизы GitHub, установкой — сама игра. Руками собирать и раскладывать архивы
больше не нужно.

---

## Три способа запустить сборку

| Что произошло | Что делает CI |
|---|---|
| пуш в `main`, pull request | тесты и clippy; дистрибутив не собирается |
| кнопка **Run workflow** во вкладке Actions | собирает Linux и Windows, кладёт архивы в артефакты сборки. Релиз **не** создаётся |
| пуш тега `v0.2.0` или `0.2.0` | то же плюс публикация релиза с обоими архивами |

Тестовая сборка — это средняя строка. Архивы висят в артефактах задания
неделю, скачиваются вручную и ничего не ломают игрокам: обновлятор смотрит
только на релизы.

Сборка дистрибутива не запускается на каждый коммит намеренно. Bevy собирается
с нуля десятки минут, и гонять это ради проверки, которая всё равно ничего не
публикует, — трата чужих машин.

---

## Выпуск релиза

Версия живёт в одном месте — `version` в корневом `Cargo.toml`. Тег обязан ей
соответствовать, и CI это проверяет **до** публикации:

```bash
# 1. Поднять версию в Cargo.toml, например 0.1.0 -> 0.2.0
#    (workspace.package.version — её наследуют все три крейта)
# 2. Закоммитить и запушить
git commit -am "Версия 0.2.0"
git push origin main

# 3. Тег с той же цифрой и ведущей v
git tag v0.2.0
git push origin v0.2.0
```

Дальше всё сделает CI: соберёт, упакует, создаст релиз и напишет список
изменений по коммитам.

**Почему версия и тег обязаны совпадать.** Игра сравнивает тег последнего релиза
с версией, вшитой в свой бинарник. Разойдутся — игрок с 0.2.0 будет получать
предложение обновиться до 0.2.0, снова и снова. Задание «Тег совпадает с версией
в Cargo.toml» падает раньше, чем такой релиз выйдет наружу.

Тег можно писать и без `v` — в репозитории уже есть такой (`0.0.1`), и игра
всё равно отбрасывает ведущую букву при сравнении версий. Важно только, чтобы
цифры совпадали с `Cargo.toml`.

Ошиблись с тегом — пересоздать:

```bash
git tag -d v0.2.0 && git push origin :refs/tags/v0.2.0
```

## Что лежит в архиве

Плоский zip, без каталога внутри: обновлятор раскладывает его файлы прямо
поверх установленных.

**Windows** (`cellborn-windows-x86_64.zip`): `cellborn-client.exe`,
`cellborn-server.exe`, `ИГРАТЬ.bat`, `client.bat`, `server.bat`, `ЧИТАТЬ.txt`,
`cellborn-server.cfg`, `МЕХАНИКА.txt`, `ЧТО-ПРОВЕРИТЬ.txt`.

**Linux** (`cellborn-linux-x86_64.zip`): `cellborn-client`, `cellborn-server`,
`играть.sh`, `cellborn-server.cfg` и те же тексты.

Ассетов в архиве нет: шрифт вшит в бинарник, остальное процедурное.

Имена архивов зашиты в двух местах — в этом workflow и в константе `ASSET` в
`crates/client/src/update.rs`. Разойдутся — обновление будет вечно говорить «в
релизе нет файла», поэтому за совпадением следит тест
`asset_name_matches_the_workflow`: он читает сам workflow и падает, если имя из
кода в нём не встречается.

## Как обновляется игрок

Кнопка в главном меню. Одна на все состояния: «Проверить обновление» →
«Обновить до v0.2.0» → «Скачиваю 47 %» → «Перезапусти игру».

Порядок операций выбран так, чтобы оборванная закачка не оставила игрока без
игры: архив сначала скачивается целиком, потом целиком распаковывается во
временный каталог рядом с игрой, и только когда оба шага прошли, файлы
переезжают на место. Прежние бинарники не удаляются, а переименовываются в
`.old` — заменить работающий исполняемый файл нельзя, а переименовать можно, и
это же оставляет путь назад. Следующий запуск их подчищает.

Размер скачанного сверяется с тем, что сообщил GitHub: оборванная закачка иначе
выглядит как успешная — сервер просто закрыл соединение.

### Конфиг сервера не трогается. Никогда.

`cellborn-server.cfg` — файл игрока. Он его правил, расставлял свои
комментарии, менял порядок строк. Обновление его пропускает.

Новые настройки при этом не теряются: сервер **дописывает** их в тот же файл при
первом запуске новой версии — в конец, отдельным разделом, с теми же
описаниями, что и в сгенерированном файле. Прежние значения остаются как были.

```
# --- Добавлено при обновлении игры ---
# Ниже настройки, которых не было в твоей версии. Значения по умолчанию;
# правь как любые другие. Твои прежние значения не тронуты.

# --- боты ---

# На каком расстоянии бот видит еду и врагов
bot_vision = 20
```

Закомментированная настройка считается отсутствующей: спрятал строку под `#` —
получишь её обратно со значением по умолчанию. Это осознанно, иначе о новой
версии ключа никто бы не узнал.

Поведение закрыто тестами в `crates/server/src/config.rs`:
`appending_keeps_everything_the_player_wrote`, `appending_is_idempotent`,
`commented_out_settings_count_as_missing`, `empty_sections_are_not_written`.

## Проверить обновлятор, не выпуская релиз

Переменная `CELLBORN_REPO` подменяет репозиторий, у которого игра спрашивает
релизы:

```bash
CELLBORN_REPO=твой-логин/cellborn-test ./cellborn-client
```

Так можно выложить черновой релиз в свой форк и пройти весь путь — проверку,
закачку, подмену файлов — не трогая то, что видят игроки.

## Уже лежащий релиз 0.0.1

В репозитории есть релиз `0.0.1` с единственным файлом `windows.tar.gz` — от
руки, до этой автоматики. Игра его не увидит: 0.0.1 старше текущей версии, а
даже будь он новее, в нём нет архива с ожидаемым именем, и обновлятор честно
скажет «в релизе нет файла cellborn-windows-x86_64.zip». Трогать его не нужно,
мешать он не будет.

## Что вшито в бинарник

`crates/common/build.rs` кладёт в сборку короткий хеш коммита и дату. Версия
берётся из `Cargo.toml`. Всё вместе видно в меню и в оверлее по F1:

```
0.1.0 (82403ac, 2026-09-01)
```

`+` после хеша означает сборку из незакоммиченного дерева — такую невозможно
воспроизвести, и в баг-репорте это важнее аккуратности строки. В релизных
сборках его быть не должно.

Собрать проект без гита (из архива, например) можно: вместо хеша будет прочерк.
